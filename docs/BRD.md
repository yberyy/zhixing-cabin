# 知行舱 BRD（商业需求文档）

版本：0.2  
状态：MVP，业务假设待真实用户验证  
产品定位：个人学习与生活的多 Agent 管理平台

## 1. 背景与机会

个人成长工具通常割裂为待办、番茄钟、习惯打卡和笔记。用户需要反复搬运上下文，也很难从“记录”走到“下一步行动”。知行舱把这些对象放进同一套个人上下文中，由多个职责清晰的 Agent 共同辅助执行。

## 2. 商业目标

- 将每日规划时间控制在 5 分钟以内。
- 提升用户每周关键行动完成率，而非单纯增加任务数量。
- 形成可解释的 Agent 建议链路，建立长期信任。
- 让多 Agent 的拆解、调用与合并过程可观察，用户能看见“为什么给这个建议”。
- 验证个人多 Agent 协作是否比单一聊天助手更能促进持续行动。

## 3. 目标用户

核心用户是需要同时管理课程、自学、作息与个人目标的学生和早期职场人。他们有明确成长意愿，但常被工具切换、计划过载与反馈滞后消耗精力。

## 4. 核心价值

| 用户问题 | 产品能力 | 业务结果 |
| --- | --- | --- |
| 不知道今天先做什么 | Orchestrator 汇总优先级 | 更快进入行动 |
| 大任务难以开始 | Atlas 拆解学习任务 | 降低启动成本 |
| 学习挤占睡眠运动 | Mira 检查生活约束 | 提升节奏可持续性 |
| 复盘流于记录 | Nova 提炼趋势和调整项 | 形成改进闭环 |
| 不信任黑箱建议 | 运行轨迹展示调用与来源 | 建议可解释、可采纳 |

## 5. MVP 范围

包含任务流、多 Agent 编排与运行轨迹、专注计时、习惯打卡、每日复盘、总览指标、浏览器与服务端两种数据模式。默认使用确定性规则 Provider，不依赖付费模型即可运行。不包含社交排行、付费体系、公开社区、医疗诊断和 Agent 自主执行高风险外部操作。

## 6. 关键指标

- 激活：首次访问 10 分钟内新增任务并完成一次 Agent 协作运行。
- 留存：连续 7 天中至少 4 天产生有效行动。
- 价值：每周完成至少 3 个“重要”任务，且用户采纳至少 1 条 Agent 建议。
- 可解释：每次运行可回溯调用顺序、来源与耗时，用户可确认或拒绝高影响建议。
- 质量：关键 API 成功率大于 99%，本地模式无数据丢失。

## 7. 风险与原则

- 建议过多导致认知负担：每次最多返回 3 个可执行步骤。
- Agent 权限不清：所有建议展示来源 Agent，高影响操作必须确认。
- 把规则引擎误认为大模型：运行轨迹必须标注 Provider 与降级原因。
- 隐私风险：MVP 默认本地优先，服务端仅保存必要结构化数据；密钥只存在于服务端环境变量。
- 指标异化：不以连续打卡惩罚用户，不把休息视为失败。

## 8. 业务假设与证据边界

| 假设 | 计划如何验证 | 当前证据 |
| --- | --- | --- |
| 学习、生活和复盘共用上下文能减少重复输入 | 观察用户完成一次目标规划需要重复解释多少次背景 | 已有统一工作台与运行级共享记忆，尚无真实对照实验 |
| 多专业视角能减少学习计划挤占生活的情况 | 对比单纯学习建议与加入 Mira 后的计划可执行性 | 已有规则冲突与确认流程，没有证明能提升长期健康或成绩 |
| 可追溯与人工确认能提高建议采纳意愿 | 记录用户对来源、权限及确认流程的理解情况 | 已有轨迹，不把页面演示值当成采纳率证据 |
| 无 Key 的完整体验有利于首次使用 | 测试用户从启动服务到完成首个目标的耗时与失败原因 | 已出现未启动服务直接打开网址的障碍，README 必须覆盖启动闭环 |

本项目尚未提供用户访谈样本、付费意愿调查或市场规模研究。商业目标是待验证目标，不是已经达成的效果，不据此宣称收益、学习成绩或习惯养成保证。

## 9. 用户场景与业务闭环

| 场景 | 输入与触发 | 用户获得的结果 | 业务成功条件 |
| --- | --- | --- | --- |
| 课程复习 | 用户提交“安排明天数学复习和作息” | Atlas 拆学习行动，Mira 检查负载，必要时 Nova 校准目标 | 用户看懂来源，接受适量行动，并保留最终决定权 |
| 计划过载 | 待办时长较多或学习/休息有冲突 | 提出压缩任务、保留休息或收窄目标的建议 | 用户确认后才修改计划，拒绝建议不妨碍继续使用 |
| 日常执行 | 选择普通任务、开始专注、完成习惯 | 更新任务状态并为复盘积累记录 | 刷新页面后数据仍可恢复 |
| 周期复盘 | 用户主动提交复盘并发起目标检查 | 基于已有任务和评分生成下一步建议 | 说明数据范围与不足，不把演示图表当成分析证据 |

用户首次使用的完整路径是：准备 Node 环境 → 启动本地服务 → 验证健康状态 → 打开网页 → 新增任务 → 发起协作 → 处理待确认事项 → 执行并复盘。交付文档必须支持用户独立走通这条路径。

## 10. 范围与优先级

| 优先级 | 业务能力 | 本版本口径 |
| --- | --- | --- |
| P0 | 启动可用、任务持久化、归档与恢复 | 本地 Node 服务提供完整体验；业务数据不得作为临时缓存删除 |
| P0 | 专业分工、受控写入与运行追溯 | 各领域 Agent 输出建议，Orchestrator 编排，用户确认高影响动作 |
| P0 | 无模型配置也可运行 | 默认确定性规则，不对外宣传为模型推理 |
| P1 | 自选模型服务 | 已实现可配置请求通道；真实账户、网络、模型权限需用户自己的服务验证 |
| P1 | 习惯与复盘 | 可记录与切换；跨日期自动结算、可靠历史统计仍有缺口 |
| P2 | 真实事件驱动的趋势与专注统计 | 页面部分为演示展示，不能用于证明业务效果 |
| 不纳入 | 自动训练、互联网检索、跨平台日历、多人账户与商业收费 | 不因配置 API Key 自动具备，也不在本版本验收中承诺 |

## 11. 指标口径与验证计划

第 6 节中的 5 分钟、7 天活跃与 99% 成功率均为目标值，不是观测结果。

| 指标 | 统计口径 | 数据准备与限制 |
| --- | --- | --- |
| 首次激活 | 同一用户从首次可用页面到创建任务并完成一次运行 | 目前没有完整用户身份与埋点，先做人工走查记录 |
| 规划耗时 | 从用户开始组织目标到得到可执行建议的时间 | 包含输入、等待模型和处理确认，不能只计算 Agent 执行耗时 |
| 建议采纳 | 高影响提案被 approve 的数量 / 已处理的高影响提案数量 | 可从 confirmations 追溯；自动新增任务不等同于主动采纳 |
| 有效行动 | 完成一项任务或保存一条有内容的复盘 | 需要按真实事件与日期统计；现有演示图表不能替代 |
| 重要任务完成数 | 完成被用户标记重要的任务数量 | 当前任务对象没有重要程度字段，暂不能自动计算该业务指标 |
| 接口成功率 | 观察期内成功请求 / 有效请求，剔除用户非法输入并单列错误原因 | 尚无持续监控平台，自动测试通过不等于达到线上 99% |

## 12. 成本、数据与运营边界

- rules 模式不调用收费模型，适合本机演示；仍需要用户运行本地服务。静态站点模式是另一种托管方式，不等于停止所有服务器后网址仍可访问。
- openai 模式需要用户自己的服务账户。一次协作可能调用多个专业 Agent，并因 handoff 增加请求；本版本没有账单汇总、令牌预算或费用硬上限。
- 启用远端模型后，目标与必要的任务、习惯、复盘和共享上下文摘要会发往配置的服务端点；产品说明必须明确这个数据流变化。
- Key 仅通过服务端配置传入，不写入前端、业务 JSON 或 Agent Markdown；当前没有内置有效 Key，也没有承诺任何账户额度。
- 本地版本按单用户、单 Node 进程运行；备份应覆盖 state.json 与 runs.json。发布给多人使用前需要另行设计认证、数据隔离、数据库事务和运营监控。

## 13. 业务交付标准

交付应包含可运行的前后端、角色/权限说明、BRD/PRD、接口契约、启动与排障文档、运行轨迹样例及真实执行过的测试记录。验收至少覆盖一次无 Key 的完整主流程、一次高影响确认与拒绝、一次归档恢复，以及一次模型失败降级。真实 Key 联调应作为单独验证项，不能用模拟端点成功替代。
